검사일: 2026-11-08. 실제 게임을 실행하지 않는 경로 설정 검사 14개를 통과했습니다. 첫 입력 후 무질문 재사용, 한글·공백·따옴표·EXE 경로, 상대 경로의 절대 경로 저장, 현재 작업 폴더 변경, 저장된 선택 우선 적용, 기존 runtime/app 자동 선택, 폴더 변경·Enter 유지·이동 후 재선택, 불완전 경로 재입력, 손상·읽기 불가 설정 복구, 원자적 저장 실패 시 기존 파일 보존·임시 파일 정리, 취소 시 기존 선택과 다른 파일 보존을 검사했습니다.

별도 Python 프로세스에서 선택 프로그램을 실행한 뒤, 새 프로세스에서 표준 입력 없이 기억한 경로를 읽는 것을 확인했습니다. Host·Join·Single·Settings의 실제 진입점을 호출하고 게임 실행 직전 처리를 대체하여 네 실행기 모두 같은 저장 경로를 사용하는 것도 검사했습니다. 게임·네트워크 프로토콜 코드는 변경하지 않았으며 v0.6.0과 같은 `rbo-ex3-lab-6.0-resume-2`를 사용합니다.

재현: `runtime/python/python.exe -B -X utf8 -m unittest discover -s tools -p test_game_settings.py -v`.

기존 검사와 합친 자동 검사 137개도 모두 통과했습니다. 이번 수정의 검증에서는 실제 게임을 실행하지 않았습니다. 배포 ZIP의 61개 파일·CRC·Python 소스 문법·개인 설정 미포함을 검사했으며, 압축에서 꺼낸 Python으로 게임 폴더 선택 후 별도 프로세스의 무입력 재사용과 실행기 모듈 불러오기를 확인했습니다.

## v0.6.0: 같은 게임에서 연결 복구·논리적 공격 자료 비교

검사일: 2026-11-08. 이번 검사는 모두 별도 게임 복사본에서 무음으로 실행합니다. 시험 실행 직전에 원래 설정 형식의 소리 모드를 3(동영상 외 무음)으로 지정하고, 동영상이 없는 복사본인지 확인합니다. 실제 설치본의 소리·키 설정 및 싱글·온라인 저장을 수정하지 않습니다. 화면 크기·텍스처 깊이·화면 갱신은 참가자별로 다르게 시험하되 소리는 모두 끕니다.

확인한 구조와 변경:

- 통신 단절은 게임 프로세스 종료와 분리했습니다. 연결이 끊기면 현재 입력 프레임에서 기다리고 비공개 참가 증표·세대·응답 순번으로 재접속합니다. 같은 요청은 동일한 결과를 반환하며, 서버가 이미 확정한 입력이나 저장 변경을 두 번 적용하지 않습니다. 불완전한 TCP 응답은 버리고 새 소켓에서 다시 받습니다.
- 응답 이력은 기본 4,096프레임으로 제한하고, 비정상적으로 이력을 벗어나거나 실제 진행 차이가 생기면 기존 스테이지 복구를 사용합니다. 정상적인 연결 재시도는 스테이지 실패 횟수를 증가시키지 않습니다. 새 연결이 자리를 인계하면 이전 소켓을 즉시 닫아 끊어진 연결이 누적되지 않게 합니다.
- 원본의 `0x427ed7/0x428025`가 기록하는 64개 스크립트 할당 정보와 `0x42bf9a`의 상대 실행 위치를 사용합니다. 공격 명령·조건은 전체 바이트코드 SHA-256, 할당 크기, 내부 위치로 비교합니다. 프레임마다 새로 읽어 변경된 자료가 캐시에 가려지지 않게 합니다. 짧은 명령 뒤의 미할당 영역을 임의로 읽지 않습니다. 설치 자료의 FOB 299개 중 가장 큰 파일은 351,532바이트로, 검사 상한(단일 4 MiB/합계 32 MiB) 이내입니다.
- 명령 저장 풀 `+0x588..+0x69f`의 사용하지 않는 노드는 next/data 두 단어 모두 비교에서 제외하고, 검증된 여섯 활성 연결 목록·순서·자료 식별자를 대신 비교합니다. 자동 직업 검사에서 2·3번 직업의 1,734프레임에 비활성 `+0x600` 잔여 주소만 달랐던 문제를 찾아 공통 구조를 수정했습니다. 좌표·캐릭터·난수·활성 명령은 그 순간 같았습니다.
- `0x448500`에서 인덱싱하는 300바이트 동작 기록과 `0x448b50..0x448bdf`에서 사용하는 활성 공격 판정·120바이트 공격 자료도 내용으로 비교합니다. `0x448d30`의 세 충돌 사각형 역시 활성 개수에 맞춰 비교합니다. 확인되지 않은 주소를 수치 모양만 보고 자동 제외하지 않습니다.
- 불일치 직전의 상세 상태를 인증된 별도 연결로 호스트에 전달합니다. `logs/<세션>/events/*-peer_diagnostic.json`에서 양쪽 자료를 비교할 수 있습니다. 크기·개수·보관 세대를 제한하며 진단 실패는 복구 실패로 취급하지 않습니다. 사용자가 게임 창을 닫는 동작은 단절된 소켓과 별도의 종료 요청으로 처리합니다.

## v0.5.4: 공격 명령 목록 전체의 주소 정규화

검사일: 2026-11-08. 실제 온라인 플레이에서 캐릭터 5·13 조합의 활 공격 이후 스테이지 복구가 반복됐습니다. 사용자의 세션은 조작하지 않고 기록을 읽었으며, 아래 게임 검사는 저장과 입력을 별도 시험 폴더로 복사해 수행했습니다.

- 같은 설정의 단순 반복 공격은 두 게임 × 3,000프레임에서 재현되지 않았습니다. 실패 직전의 실제 입력 1,562프레임을 복원하고 서로 다른 화면 크기·화질·소리 설정을 적용하자 `bow-replay-mixed-v053`의 1,560프레임에서 상태 불일치가 재현됐습니다.
- 첫 차이는 객체 65의 `+0x59c` 한 단어였습니다. 캐릭터 기록·난수·객체 수·위치·그 밖의 비교 대상 객체 값은 같았고, 해당 값은 서로 다른 주소였습니다. 원본의 `0x422b29`는 객체 `+0x588`부터 8바이트 간격의 명령 노드를 만들고, `0x422930`은 노드의 `+4`에 명령 자료 주소를 기록합니다. `+0x59c`는 세 번째 명령 자료 주소입니다.
- `+0x588..+0x69f`의 35개 노드 전체와 `+0x6a0..+0x6c8`의 여섯 연결 목록을 공통 처리합니다. 자료 주소만 정규화하고, 활성 명령의 앞 64바이트·노드 위치·목록 구분·연결 순서는 비교합니다. 비활성 노드의 남은 주소는 읽지 않습니다. 범위 밖 링크·중복 노드·활성 명령의 빈 주소는 거부합니다.
- 수정 후 `bow-replay-fixed-v054`: 동일 입력과 설정으로 두 게임 × 1,700프레임, 53.22초, 정상 종료 2개, 입력·검사 상태·시험 세이브 일치. 실제 사용자의 온라인 저장은 검사 전후 SHA-256이 같았습니다.
- 명령 구조 검사 8개: 1~35개 활성 노드의 주소 이동, 모든 35칸의 내용 변경 감지, 여섯 목록의 구성과 연결 구분, 비활성 주소, 게임 좌표 차이, 잘못된 링크·순환을 검사합니다. 통신 36개와 자동 복구 12개 검사도 통과했습니다.

이 수정은 특정 공격의 예외를 추가하는 방식이 아니라 확인된 공통 자료 구조 전체를 처리합니다. 단, 가변 길이 명령 전체·모든 힙·미확인 전역 변수까지 검증하는 구조는 아니며, 기존 객체 비교에 아직 알려지지 않은 주소나 표시 값이 남아 있을 가능성도 있습니다. 모든 직업·스킬을 시험한 결과로 확대 해석하지 않습니다. 미확인 차이를 자동으로 무시하거나 실제 진행 차이의 복구를 비활성화하지 않습니다.

자동 검사: `runtime/python/python.exe -B tools/test_entity_commands.py`, `tools/test_netplay.py`, `tools/test_netplay_recovery.py`. 실제 재생에 쓴 사용자 입력·캐릭터·게임 자료는 공개 배포에 포함하지 않습니다. 변경된 상태 비교를 이전 실행기와 섞지 않도록 통신 버전을 `rbo-ex3-lab-5.4`로 구분했습니다.

정상 메뉴 입력 처리 전의 `0x43d4cc`에서 네트워크 프레임을 교환합니다. 1P 로컬 설정을 연결별 슬롯으로 전달하고, 원래 게임이 키의 눌림·떼짐을 계산합니다. 공통 메뉴 소유자는 1P로 정하며 캐릭터 생성에서는 각자 입력합니다. 첫 지도 추천은 1스테이지로 바꾸고 이후 원래 다음 스테이지 추천을 유지합니다.

로컬 고해상도 시계와 밀리초 시계를 120Hz 공통 시간으로 바꿉니다. 메뉴 전환이 각 PC의 효과음 재생 완료를 기다리던 `0x476fe0`, `0x406960`, `0x4069b0`, `0x457790`은 소리 대기만 생략하고 기존 프레임 기반 화면 전환을 유지합니다. 이 함수들은 `0x41a190`을 통해 소리 버퍼 재생 상태를 읽습니다. [Microsoft의 GetStatus 설명](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee418070(v=vs.85))도 소리 출력 지연과 상태 변경 시점의 차이를 설명합니다.

초기 3인 메뉴 검사에서 160프레임의 화면 전환이 한 프레임씩 달랐습니다. 공통 시계 적용 후에도 간헐적으로 재현되어 소리 대기 조건을 추가로 수정했습니다. 이후 메뉴와 스테이지 전환 검사에서 해당 차이가 재현되지 않았습니다.

일반 캐릭터로 첫 전투에 진입할 때 객체 `+0x584`가 프로세스별 자료 주소를 포함해 잘못 불일치로 판단했습니다. `0x4229ef`에서 저장하고 `0x423686`→`0x423620`에서 읽는 명령 자료 포인터임을 확인했습니다. 주소는 정규화하고, 유무와 앞 64바이트 내용을 해시에 포함합니다. 전체 자료 길이나 모든 힙을 검사하는 것은 아닙니다.

이전 실제 인터넷 세션은 48,988프레임의 상태 불일치로 종료됐습니다. 시간 제한 종료는 아니었습니다. 그 세션의 친구 원시 자료가 없으므로 위 수정 사항이 당시의 정확한 원인이었다고 확정하지 않습니다. 현재는 최근 프레임의 객체 원시 자료와 메뉴·난수·캐릭터·위치 비교 정보를 별도로 보존합니다.

일반 플레이의 리플레이 녹화 부분은 생략해 고정 녹화 공간과 25/30분 경고를 사용하지 않습니다. 캐릭터 저장은 별개로 유지합니다. 온라인 리플레이는 지원 범위가 아닙니다. 게임 프로세스의 비정상 종료 코드를 정상 종료와 구분합니다.

호스트가 창을 닫았을 때 서버가 친구의 종료 안내 수신보다 먼저 소켓을 닫는 문제가 실제 실행기 검사에서 재현됐습니다. 정상 종료 시 최종 저장·종료 안내를 전송하고 핸들러가 마칠 시간을 준 뒤 닫도록 수정했으며 재검사했습니다.

### 저장 범위

호스트의 검증된 JSON 체크포인트를 새 임시 게임 저장 폴더에 적용합니다. 실제 게임이 저장하면 호스트가 파일을 읽고, 해당 프레임의 상태 일치 확인 후 사본을 전원에게 전송합니다. 파일 이름·크기·기본 형식을 허용 목록으로 검사하며 원본 게임 저장 경로에는 쓰지 않습니다. 현재 파일은 임시 파일의 디스크 기록 완료 후 교체하고 이전 버전은 history에 보관합니다.

## v0.3.0: 플레이 시간 제한 제거

검사일: 2026-11-08, 한국 시간 기준. 자동 검사는 한 PC의 분리된 EX3 프로세스와 로컬 TCP 서버를 사용합니다.

기본 프레임 한도를 0(무제한)으로 바꿨으며, 서버와 참가 프로그램은 연결이 종료될 때까지 순서가 있는 입력을 교환합니다. 기존 실행기의 900초 디버거 기한도 기본 실행에서 제거했습니다. 오류 감지와 연결 대기 시간 초과는 유지합니다.

게임의 데모 타이머 함수 `0x438fb0`는 `0xbc7bd0`에서 10,800부터 감소하는 값을 검사하고, 호출부 `0x43c259`는 만료 시 데모를 종료합니다. 실행 중인 시험용 프로세스에서 이 만료 결과만 0으로 바꿨습니다. 원본 실행 파일은 변경하지 않습니다.

기존 입력 게이트 `0x438e80`의 재생 커서 `0xadeb28`은 해당 입력 배열을 읽는 용도입니다. 매 틱 커서를 0으로 되돌리고 첫 3바이트에 새 입력을 쓰도록 바꿨습니다. 네트워크 프레임 번호는 별도의 Python 정수로 계속 증가합니다. 따라서 원래 기록 길이 이후의 메모리에 입력을 쓰지 않습니다.

통신 검사 28개를 통과했습니다. 2인·3인 무제한 방을 각각 8,500프레임까지 실행한 뒤 호스트 또는 마지막 참가자가 종료하는 네 경우를 포함합니다. 모든 경우 상태 오류 없이 종료 신호가 전파됐고, 서버 기록은 최근 4,096개로 제한됐습니다. 기존 숫자 상한 200,000 이후 프레임도 무제한 방에서 처리하는지, 상태 불일치는 정상 종료로 숨기지 않고 오류로 처리하는지 검사했습니다.

실제 2인 게임은 24,000프레임을 완료했습니다. 각 게임의 DirectInput 키 변환 경로에 동일한 Z키 시험 입력을 넣었고, 7,200프레임 한도·약 10,425프레임의 이전 데모 종료 시점·22,440프레임의 원래 기록 길이를 모두 넘겼습니다. 입력 및 검사 대상 상태 차이 0건, 클라이언트당 객체 기록 239,981개를 비교했습니다. 이 유한 길이는 검사를 끝내기 위한 값이며 기본 실행의 한도가 아닙니다.

3인 무제한 방의 자동 전투는 사용자의 검사 단축 요청으로 중도 종료했습니다. 호스트 시험 게임 프로세스를 닫기 전까지 공통 7,789프레임의 입력과 검사 대상 상태가 일치했고, 세 참가자가 정상 종료했습니다. 호스트는 7,789프레임, 두 친구는 각 7,792프레임을 기록했습니다. 원래 목표 24,000프레임을 완료한 것으로 계산하지 않습니다. 추가 실행기 실기 검사는 생략했습니다.

무제한 프레임 기록은 8MiB × 최대 3개 파일을 순환합니다. 개발용 유한 프레임 검사 또는 전체 기록 옵션은 별도입니다.

v0.2.0에서 사용자가 친구의 외부 인터넷 접속 및 게임 창 표시를 확인했습니다. 해당 외부 세션의 장시간 상태 비교 로그를 수집한 것은 아닙니다.

## v0.2.0: 2인·3인 선택

검사일: 2026-11-08, 한국 시간 기준. 한 Windows PC에서 분리한 EX3 프로세스와 `127.0.0.1` TCP 서버를 사용했습니다. 다른 PC와 외부 인터넷에서 수행한 결과가 아닙니다.

2인·3인 각각의 입력 분리, 준비 대기, 정원 초과, 연결 종료, 상태 불일치, 이전 프로토콜 거부 등을 포함한 통신 검사 25개를 통과했습니다. 2인 방은 호스트와 친구 한 명이 준비하면 시작하며, 모든 프레임에서 세 번째 입력은 0으로 고정합니다. 초기 상태의 세 번째 캐릭터도 비활성화합니다.

수정 후 2인 자동 전투는 게임 2개 × 7,200프레임을 정상 종료했습니다. 입력·검사 대상 상태 차이는 0건이었고, 클라이언트당 객체 기록 208,271개를 비교했습니다. 모든 프레임에서 두 캐릭터만 활성 상태이고 세 번째 입력이 0임을 검사했습니다. 화면에서도 세 번째 칸이 `Empty...`인 것을 확인했습니다.

2인 동일 Z키 검사는 게임 2개 × 2,400프레임을 정상 종료했습니다. 각 게임의 DirectInput 버퍼에 같은 Z 스캔 코드를 넣어 실제 키 변환 경로를 통과시켰습니다. 1P만, 2P만, 아무도 입력하지 않음, 두 명 동시 입력을 각각 120프레임씩 검사했고, 클라이언트별 입력 240프레임이 지정된 슬롯에만 전달됐습니다. 입력·검사 대상 상태 차이는 0건입니다. 물리 키보드를 누른 새 검사는 아닙니다.

기존 3인 모드는 게임 3개 × 2,400프레임 자동 전투로 다시 검사했습니다. 클라이언트당 객체 기록 83,808개를 비교했으며, 입력·검사 대상 상태 차이 0건으로 세 게임 모두 정상 종료했습니다.

실제 호스트·참가 실행기 검사는 2인·3인 각각 120프레임으로 수행했고 모든 실행기가 정상 종료했습니다. 2인 검사는 인원 질문에 Enter를 입력하는 기본 선택 경로까지 포함합니다.

2인 자동 전투의 첫 검사에서는 4,190프레임에서 상태 해시 차이로 중단됐습니다. 원시 객체 기록을 비교한 결과, 캐릭터 정보·난수·위치·객체 구조는 같았으며, 새로 사용된 객체 필드 `+0x7f8`의 프로세스별 주소가 달랐습니다.

실행 파일의 `0x448e35`는 `+0x7f8/+0x7fc`에 최대 두 개의 8바이트 사각형 기록을 가리키는 포인터를 저장합니다. `0x44896d`에서 이 값을 `0x4487c0`에 전달하며, 네 개의 16비트 좌표를 읽습니다. v0.2.0에서는 두 주소 자체를 정규화하고 **활성 기록의 실제 8바이트 내용은 상태 해시에 추가**했습니다. 단순히 차이가 나는 게임 값을 무시한 수정은 아닙니다.

후속 검사에서 4,287프레임에 발견된 `+0x594`도 주소 필드였습니다. `0x422b29`와 `0x422930`이 만드는 8바이트 간격 목록의 두 번째 자료 포인터로, 이미 정규화하던 `+0x58c` 다음 항목입니다. 이 주소도 정규화 목록에 추가했습니다. 따라서 현재 객체의 주소 필드 18개와 표시 필드 6개를 정규화합니다. 사각형 외의 전체 참조 자료와 전체 힙은 여전히 상태 해시의 대상이 아닙니다.

수정 후 4,000~7,199프레임의 별도 원시 캡처 비교에서는 정규화 대상 외의 객체 필드 차이가 없었습니다. 사각형 자료 55건과 `+0x594`가 가리키는 자료의 앞 64바이트 2,387건도 두 게임에서 모두 같았습니다. 이는 해당 구간의 보조 검사이며 전체 참조 자료를 검사한 것은 아닙니다.

통신 검사는 동일 입력의 분리와 순서, 호스트 슬롯 예약, 다른 슬롯 지정 금지, 잘못된 방 코드·게임 파일·프레임 순서·입력 값·초대형 패킷 거부, 상태 불일치 및 연결 종료 처리를 포함합니다.

### 비교한 상태

캐릭터 기록 3개, 난수 상태 3개, 활성 객체 목록과 자식 구조, 각 객체의 0x974바이트 기록을 비교합니다. 객체의 위치도 포함합니다. 프로세스별 포인터 주소 필드 15개와 확인된 표시 효과 필드 6개는 해시에서 제외합니다.

전체 힙과 전역 변수, 메뉴, 저장, 모든 스테이지를 검사한 것은 아닙니다. 같은 해시가 모든 게임 상황의 동일 진행을 보장하지 않습니다.

### 발견한 제한

12,000프레임 무입력 시험은 약 10,425프레임에서 기존 데모가 화면을 전환하여 완료하지 못했습니다. 이 결과를 근거로 공개 실행기의 세션을 최대 7,200프레임으로 제한했습니다. 진행이 멈추면 세션을 끝내는 감시도 추가했습니다.

현재는 고정 초기 상태의 시험 스테이지만 지원합니다. 일반 스테이지 진행, 메뉴와 저장, 재접속, 롤백, 인터넷 지연·손실, 다른 PC, 사용자 지정 키, 패드는 후속 개발·검증 대상입니다.

## 재현 (v0.2.0)

Python 3.12 이상에서 통신 검사:

```console
python -B tools/test_netplay.py
```

게임 검사는 64비트 Windows에서 실행합니다. 별도로 준비한 일본어판 EX3 4.0과 모든 기본판·확장팩 PAC를 `runtime/app`에 두고 `analysis` 폴더를 만든 뒤 실행합니다. 실행 파일 해시는 README에 명시한 값이어야 합니다.

```console
python -B tools/test_netplay_game.py --tag two-player-check --players 2 --frames 7200
python -B tools/test_netplay_game.py --tag two-player-keyboard --players 2 --frames 2400 --keyboard-test
python -B tools/test_netplay_game.py --tag three-player-check --players 3 --frames 2400
python -B tools/test_netplay_launcher.py --tag two-player-launcher --players 2 --prompt
python -B tools/test_netplay_launcher.py --tag three-player-launcher --players 3
```

각 태그는 새 이름을 사용합니다. `--live`에서는 실제로 게임 창을 선택하고 키를 눌러야 키보드 입력까지 검사할 수 있습니다. 게임 창이 여러 개 나타나고 검사 종료 시 자동으로 닫힙니다. 원본 대신 임시 경로의 분리된 게임 복사본을 사용합니다.

원시 실행 로그와 메모리 캡처는 공개 저장소·배포 압축에 포함하지 않았습니다.
